# HUD approximately 40 FPS

User target: approximately 40 real on-board FPS, keeping scale-label fading and the latest selective-digit rolling behavior. The latest user instruction supersedes timed holds: digits are driven continuously by the same axis value, with no hold or transition timer. Short-stroke motion was rejected. Existing automatic flash authorization applies.

Baseline final 25 FPS version: docs/hud-performance-board-measurements.json and docs/hud-performance-validation.md. Program 642034, static RAM35156, IMU200Hz. A 70s follow-up includes user swiping to attitude then back to HUD; inspect modes before calculating sustained FPS.

- Preserve the current renderer and built image in build/hud-40-baseline.
- Profile/reduce font interpolation cost with bounded output error or exact output. Keep bitmap shapes, sizes and antialiasing; validate all pixels against the pre-change renderer.
- Reduce transferred black area while preserving full restore on mode/generation change, clearing all prior ink, even-aligned windows, scan order and exclusive buffer ownership.
- Benchmark each change independently on-board using the same HUD demo. Reject changes without meaningful improvement or with degraded visuals/stability.
- Validate tests, animation, edge fading, touch/mode changes, memory and actual completed-frame FPS. Flash automatically and leave real-IMU HUD selected.

## Implemented outcome

Exact float raster optimizations, cached command bounds, changed-region reconstruction, immutable command-list swapping, dual-core internal-scratch drawing, queued DMA window batches and CPU1 command preparation are implemented. CPU0 draws every third region; a half/half region split measured slower and was rejected. Final measurements and limits are recorded in [validation](../../hud-40-validation.md). Approximately 40 FPS remains a performance target, not a guaranteed frame rate.
